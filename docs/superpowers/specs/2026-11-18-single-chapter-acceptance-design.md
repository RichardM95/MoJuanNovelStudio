# 阶段0/1：固定基线与原创单章闭环验收

用户批准新版路线：更深入而非更大，阶段0列清实现/自动化/真实环境/未验及证据，阶段1用原创虚构样本贯通保存→agent建议→人审→采纳或拒绝→结果核对→关闭重开→TXT导出。基线源码9d45ef19b00659b456f093396513c3a3a216db6c，Library v6；全套334标准Rust+13真实stdioSQLite，312UI/31及构建通过。这是自动化，不是原生安装验收。

## 边界与取舍
只增加可复现验收资产、测试和事实文档，不新增业务功能/工具，不接模型、不外发稿件、不用用户电脑，Windows暂停。若发现实际产品缺陷，先以最小失败案例报告controller，不掩盖、不因赶验收放宽断言。原目标20–30章为长期样本，当前仅两个短章：一章已保存前文、一章目标。不能称长篇性能或语义验证完成。

选择共享原创fixture用于真实Service/Broker/stdio测试和实际React App的虚构桥测试，明确它们是两个层次，不伪装为完整native IPC e2e。测试作者动作由可信测试代码模拟，不向生产外部agent增加采纳/审核方法。agent建议是固定的测试稿件，不代表模型生成或遵守设定能力。

## 样本
制作一个原创中文小故事，例如《雾港校钟人》（标题可自行定），仅虚构人事地点。一个作品、一个卷、前文与目标章；短而可读，含中文、emoji、CRLF的明确字节边界片段。至少设定卡、目标章大纲、角色卡，以及一条已知伏笔资料供依据引用。正文的客观规则和作者待审点写进样本清单，例如人物不能离开值守岗位、钟响次数、物件来源，但不将机器字面检查当文学语义结论。提供原稿、满足显式规则的固定候选稿、故意违背一条规则的候选稿、未保存作者草稿。语义对照只用于模拟作者判定conforms/conflict，必须标明作者脚本化决定。

尽量一个JSON数据源，Rust include_str与TS测试共享，避免各自拷贝漂移。fixture不得包含真实姓名地址秘密、已有用户稿件、模型凭据。README列作品结构与当前样本规模，不把素材数量当验收覆盖率。

## 自动化闭环
1. 真实Rust Service创建作品/卷章/资料并保存原稿，验证重开后原文不变。
2. 在独立测试工件子进程中用真实OS stdin/stdout JSON/MCP → AgentBroker → Service提交固定严格建议，测试授权范围、依据引用、幂等；提交不改正文。允许复用既有harness，但测试必须清楚独立计数，不能把mock当真实pipe。
3. 可信测试作者读差异并写逐卡审阅：正常候选经明确采纳后正文/历史/决定版本一致；反例候选被拒绝（或作者标conflict阻止采纳），正文不变。agent不能调用作者审核/采纳。
4. 核对确切结果，关闭Service/子进程并重新打开同一隔离SQLite；正式正文/历史/提案决定保留，不能重复采纳。按实际TXT导出服务生成文件，校验输出字节与预览/指定格式一致，只在隔离临时目录。
5. 至少一个接受事务中途注入故障，验证正文、历史、决定均无半写，移除故障后新的明确作者动作按真实语义执行；不得把已失败但状态未知时自动重发当产品行为。

## React关键边界
实际App组件+共享样本+虚构桥，串起保存、建议展示/作者审阅、明确决定、结果核对、暂离/重开及导出交互的主要路径；桥只模拟真实返回格式，不宣称真实Rust联动。可复用现有App fixtures但增加可读的单章场景，而不是只写纯函数测试。

必须以精确状态/调用/字节断言覆盖：丢失或错误决定回执；同版本异正文；未保存稿恢复不写不覆盖；重复点击/重开不重发；换库及迟到结果不发布旧稿；只读等待可停止。失败用例不仅“没有抛错”，还验证原稿/草稿保留、没有额外mutation及正确未核实/历史状态。必要时引用既有持久边界测试作为证据矩阵的一部分，不复制一整套无差异测试；新原创闭环至少有连贯正例和拒绝反例。
