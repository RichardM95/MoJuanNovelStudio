# 正文保存中断与丢回执验收

这项 Linux 云端验收对照同一临时 SQLite 样本的两份副本：一个虚构作品、一卷、1,000 个短章记录。999 章仅为短占位，不是规模计时使用的语料，也不代表千章长篇的容量或性能。目标章的原稿和两次更新尝试均经生产 `Service::apply(SaveChapter)`；两份副本由生产快照函数生成。启动子进程前确认两库的完整作品数据、目标历史和审计一致。

| 对照 | 注入或动作 | 子进程退出后由父进程重开数据库核验 |
|---|---|---|
| 提交前失败 | 仅在第一份副本安装 SQLite 测试触发器。触发器看到目标章已写入新正文和 revision 2、历史也含同一份准确字节，才中止事务中随后发生的审计写入。子进程确认收到这次注入的错误后退出。 | 正文仍逐字等于 v1，历史完整保留 v0/v1，审计和全库其他数据不变。 |
| 已提交、无应用回执 | 另一子进程调用同一生产保存，事务和 `Service::apply` 的提交后回读均成功才用 `process::exit` 退出，不发送应用层保存回执，不走正常的 Service/SQLite 析构。退出码只作验收诊断，不是应用回执。 | 正文逐字等于 v2（含中文、emoji、CRLF/LF），保留精确 v0/v1 并只新增一条对应 v2 的历史及保存审计。两次用原预期 revision 1 重试（同稿和不同稿）均收到 `revision_conflict`；再次关闭重开确认没有覆盖或重复历史/审计。 |

```sh
cargo test --locked --offline --manifest-path src-tauri/Cargo.toml --test save_recovery
```

提交前分支是可重复的 SQLite 故障注入，不是进程强杀；提交后是验收子进程截断回执，不是原生 Tauri/IPC 回执实测。未填满磁盘，也未模拟断电、文件系统故障、Windows 或真实用户稿件。没有修改产品接口或向生产库加触发器。

## 编辑器在回执不明时的核对与保稿

保存拒绝或应答里的活动章、版本、正文字节不吻合时，显示「保存结果未确认，稿件保留在编辑器」。自动保存、再次按保存或打开历史都不会重发不明的写入。选章时后台使用现有的书库标识和单章读取校准原版本、章与正文；不等待它才保存。如果不具备可核准的最初读回（例如权限、响应或书库变化），停留在保稿状态，不能从迟到结果补推旧请求身份。

「核对已存正文」只读取。相同书库标识前后核对，且看到同章恰好下一版本、内容逐字吻合，才确认上一份稿的已存状态；更晚修改不被覆盖，必须显式保存。若仍看到原版本和原文，界面只说明当前如此，**不**因通用的桥接错误推断旧请求永远不会提交，也不解锁重试。看到不同内容、不确定范围或读取失败也不会写入。可停止等待只读核对，迟到的检查不应用状态。

可显式复制当前稿件；剪贴板拒绝或不可用时，界面选中当前编辑器正文并提示手动复制。剪贴板受系统权限影响；未验证原生剪贴板，也没有将草稿另写入持久存储。未确认稿仍受离开保护，不提供独立的丢弃草稿入口；务必先手动保留正文再关闭。不是崩溃自动恢复。

```sh
npm test -- tests/AppSaveRecovery.test.tsx tests/saveQueue.test.ts tests/SingleChapterAcceptance.test.tsx
```

前端用模拟桥区分原稿仍在与旧写已提交但回执丢失，也验证手动复制、迟到结果和新稿保护；上节真实 SQLite 验收解释两类结果为何不能凭错误提示判定。不是 Windows、原生 IPC 或真实断电验收。
