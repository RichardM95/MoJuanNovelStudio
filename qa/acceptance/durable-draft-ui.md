# 意外重开后，先对照本地恢复副本

恢复副本与正文保存是两件事。选择一个活动作品中的章，应用通过现有的书库标识及针对该章的精确基线读取验证范围。只有来源可确认时，编辑后去抖才尝试写本地恢复副本；点击「保存」仍由原正文服务处理，不等副本先写。书库标识、存档版本、正文或所属范围不匹配时，不迁移、不合并，也不自动替换稿件。

重开时，若找到可比较的副本，界面分别显示当前已存正文和副本，可用只读文本区域手动复制。基线不一致时只能比较和复制；符合当前基线，也要显式点击「载入副本继续编辑」，再核对同一最新版副本及同一已存正文。这一步不写正文、不创建新副本、不启动自动保存；编辑器仍未保存，直到作者显式保存。较晚输入、选章、应用切换或换书库期间返回的结果不会应用到当前编辑器。

当正文恰好已是在该次存档版本上的副本，副本不会再作为可编辑候选出现。正文在较晚的版本恰好同文字，不能证明原写入凭据仍有效，仅提供对照。不主动删除、自动覆盖其他编辑流的未处理副本或把它写进正文历史。副本尚未确认、读写失败、候选过旧或超过单章 10 MiB 都不等于新的已存正文；请先保留编辑器中的文字。正常正文保存不依赖这条恢复通道成功。

```sh
npm test -- tests/AppDurableDraft.test.tsx tests/AppSaveRecovery.test.tsx tests/saveQueue.test.ts
```

该前端组件验收使用模拟桥，不是原生 Tauri、Windows 系统剪贴板、真实用户稿件或物理断电测试。独立 Rust 验收另测真实数据库边界；没有收到确认或还没写出的文字，不能承诺在重开后恢复。

## 边界与保留

这里的副本是同机、独立 SQLite 数据。它不是额外加密的备份，不进入正文导出、版本历史或书库备份。本版不会删除旧副本：过期副本仍占同章的保护位置，即使手工复制后另存成了更新版本，也可能继续挡住该章的新检查点。它不影响正式保存；本版没有弃用或清理界面。恢复书库后旧书库的副本仍留在本机，但不会被自动显示在复用相同 ID 的章上。保留的副本也消耗容量：最多 1,024 个位置、合计 64 MiB 的基线与副本文字字节，单份正文最高 10 MiB。这些不是整个本地数据库的文件大小。

副本需先核实书库与章节，再在输入暂停至少约 450 ms 后尝试写入。早期还未绑定的输入、不断输入而没有足够停顿、写入未确认或失败时，最后一段稿件都可能尚无可用副本。只有本次副本明确确认后，才能把那一次看到的输入当作已留有副本，仍不等于正式存稿。
